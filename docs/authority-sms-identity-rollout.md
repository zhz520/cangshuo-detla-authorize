# 短信与实名用量：接入和验收

## 授权中心

- 「短信服务」维护阿里云账号、签名、场景模板、项目计费方式、单价和套餐。按量、套餐、混合可独立选择；混合先使用最早到期且足额的套餐。
- 「短信服务 → 模板管理」提供「初始化验证码模板」。首次配置点击后会创建 `otp_login`、`otp_reset`、`otp_bind_old`、`otp_bind_new`、`otp_wechat_bind` 五个模板；如果已有启用的验证码模板，会复制其签名、阿里云模板 Code 和变量配置，再按需修改。
- 管理员在「短信服务 → 接入配置」录入阿里云账号、Secret、签名及回执签名密钥；「实名用量账户」可选择阿里云二要素（推荐）、腾讯云二要素或自定义 HTTPS 接口。阿里云模式只需 AccessKey ID/Secret，授权中心直接调用 `cloudauth.aliyuncs.com` 的 `Id2MetaVerify`；腾讯云模式只需 SecretId/SecretKey 和地域。保存立即生效，后台不回显 Secret。新安装自动在持久化目录生成 0600 的服务加密密钥；备份须包含此文件，不写入版本制品。
- 阿里云 `Id2MetaVerify` 后付费 0.2 元/次；`Code=200` 且 `ResultObject.BizCode` 为 `1`（一致）/`2`（不一致）计费；接口异常、`BizCode=3`（无记录）不扣费。
- 腾讯云 `IdCardVerification` 后付费 0.3 元/次；结果码 `0` 一致、`-1` 不一致，均按次计费；`-2` 身份证号非法、`-3` 姓名非法、`-4` 证件库服务异常、`-5` 无此身份证记录、`-6` 权威比对升级、`-7` 当日次数超限不扣费，预占释放并返回明确提示。API 密钥错误或权限不足同样不扣费。
- 自定义实名供应商接口约定：`POST` JSON `{"name":"姓名","idNumber":"身份证号"}`，请求头 `Authorization: Bearer <令牌>`，返回 JSON `{"matched":true|false,"requestId":"可选"}`。
- 启用阿里云 `SmsReport` 队列消费。可信消费者将消息体交给 `node scripts/forward-aliyun-sms-receipts.mjs`；设置 `AUTHORITY_SMS_RECEIPT_ORIGIN` 和与管理员录入一致的回执密钥。转发成功才确认原队列消息。不要把未鉴权的回调直接连到账本接口。
- 短信发送接口受理只预占额度。回执以 `OutId` 与 `BizId` 关联；成功结算一次，失败释放。旧版仅受理数据单独显示，不推断送达。断网、回执缺失或历史预占，先核对上游明细再手动释放；释放后不会追扣。短信条数按每次单收件发送统计，套餐消耗按模板配置的单位计算，两者不等同于运营商拆分的长短信段数。
- 「实名用量账户」按实例查看核验次数、匹配/不匹配、余额与额度；修改套餐不会改变新代码已经保存的订单快照。旧订单没有数量及有效期快照时，先人工核对真实订单，不按新套餐配置推断。
- 实名当前仍是姓名 + 身份证号二要素。用户自主核验、人工补提、打手提现使用各自的现有校验；年龄自报弹窗不代表实名认证。手机号三要素或活体应另开供应商能力和业务策略，不能把二要素结果视为更强验证。

## Delta 客户实例

- 从授权中心生成各实例独立凭据；服务端使用 `AUTHORITY_GATEWAY_SECRET_<实例UUID大写且用下划线分隔>`。不跨实例复用。同一凭据用于服务端签名，不下发浏览器。
- 「系统管理 → 短信服务」可选择「授权中心」或「阿里云短信（本实例配置）」。授权中心模式开验证码前需有 `otp_login`、`otp_reset`、`otp_bind_old`、`otp_bind_new`、`otp_wechat_bind` 可用模板；阿里云直连模式由客户填写自己的 AccessKey、签名和验证码模板 Code，费用由阿里云账户直接扣取。客服提醒等业务规则仍留在客户侧。
- 「系统管理 → 实名服务」要求有效授权且本地已启用。设置、套餐购买、核验接口都在服务端校验。关自动二要素保持原本的人工审核入口，不会让未核验用户自动通过。
- 购买依赖授权中心的项目和支付提供方均已开启微信 Native。套餐支付成功通知需通过签名、金额与商户校验，账务和发放重复回调只生效一次。
- 老的客户阿里云字段在「阿里云短信」模式下继续可用；切回授权中心模式后仍保留在配置中，不会被浏览或保存动作删除。

## 上线前验证

1. 在 520 隔离环境，用已审核的测试模板验证实际收件、回执成功计费、失败释放及重复回执。再测验证码用途、提醒场景、限额和耗尽后的行为。
2. 在测试账户验证二要素供应商的匹配/不匹配/异常，核对套餐消耗与账单，走通人工审核及提现收款人校验。
3. 使用测试支付账户购买短信及实名套餐，核对实际回调和发放，验证未购买/过期/未启用/错域的直接 API 均无法使用付费能力。
4. GitHub Actions 的通过状态必须以新提交的实际运行记录确认。本地模拟支付、回执和浏览器结果不是生产联调。
